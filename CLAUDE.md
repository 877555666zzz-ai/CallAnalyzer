# Call Analyzer — контекст проекта

Читай этот файл первым в любой новой сессии по этому репозиторию — экономит повторное объяснение бизнес-логики и архитектуры.

## Что это за система (бизнес-смысл)

Заказчик — отдел продаж корпоративного такси (Yandex Taxi corp, Казахстан). Менеджеры обзванивают лиды
(в том числе «тёплые» из Bitrix24), звонки пишутся телефонией. Раньше руководитель мог узнать качество
звонка только прослушав его целиком. Эта система делает это автоматически и в масштабе:

**Сквозной пайплайн:** телефония (запись звонка) → распознавание речи (STT) → анализ через LLM → база →
дашборд для руководителя/РОП + карточка сделки в Bitrix24.

Система не просто транскрибирует — она даёт **готовый вывод о деньгах**: где теряем лида (на каком этапе,
по чьей вине — менеджер или база), какие нарушения регламента были у оператора, что можно спасти при
доработке. Итоговый артефакт для бизнеса — отчёт «где деньги» (`/`, см. `src/report_money.py`), а не сырой
транскрипт.

## Телефония — миграция Sipuni → Kcell (код готов, живой ключ ещё не подключали)

Проект **изначально написан под Сипуни** (`src/sipuni_client.py`). Компания перешла на **Kcell ВАТС**
(`src/kcell_client.py`) — **Sipuni полностью отключается** (не параллельно, решение владельца), но файл
пока не удалён (легаси-путь на переходный период). Провайдер выбирается фабрикой:

- `src/telephony.py::get_telephony_client()` — `TELEPHONY_PROVIDER=kcell` (дефолт) `|sipuni`.
  Оба клиента реализуют один контракт (`export`, `download_record`, `operators`, `map_row`,
  `has_recording`) — `pipeline.py` от конкретного провайдера не зависит.
- **Ключевое отличие Kcell от Sipuni**: оператор адресуется **логином** (`user` в истории звонка),
  а не внутренним номером. `Manager.internal_number` (легаси Sipuni) и `Manager.kcell_login` (новое)
  сосуществуют в одной таблице — `store.find_manager(session, key)` ищет сначала по `kcell_login`,
  потом по `internal_number`. Для существующей боевой БД (Railway Postgres — там ещё старая колонка
  `sipuni_internal_number`) миграция не происходит сама по себе (`Base.metadata.create_all` не трогает
  существующие таблицы) — нужно один раз прогнать `python tools/migrate_manager_keys.py --apply`
  **до** первого `setup_managers.py --apply` на Kcell.
- **Kcell отдаёт запись звонка готовой ссылкой** (`record` в строке истории), не по call_id как Sipuni —
  поэтому `download_record(call_id, record_url)` у обоих клиентов принимает `record_url` (Sipuni его
  игнорирует, только для унификации интерфейса).
- **Пагинация `/history/json` не подтверждена документацией** (пример ответа — голый список без `info`).
  `KcellClient.export()` подстраховывается: режет период на окна по дням + дедуплицирует по `uid`,
  вместо того чтобы верить в один запрос = весь период. Если на живом ключе подтвердится `info.next` —
  учтено, но не проверено вживую.
- **Стерео/моно записей Kcell не задокументировано** — критично для диаризации (см. раздел про роли
  ниже). Перед первым боевым прогоном на реальном ключе: `python tools/probe_record.py`.
- **Экономия на пустых звонках**: `Pipeline._process_row` теперь отсеивает `duration<=0` или
  `has_recording=False` ДО скачивания записи и STT/LLM (`stats["no_audio"]`) — не тратим деньги на
  недозвоны, которых у телефонии в среднем много.
- **Вебхук вместо опроса** (второй этап, после того как заработает обычный polling через
  `run_production.py`/`scheduler.py`): `POST /webhook/kcell` в `dashboard/app.py`, проверка `crm_token`
  из `KCELL_CRM_TOKEN`, обработка `cmd=history` в фоне (`BackgroundTasks`) через
  `Pipeline.process_single(row)`. Остальные `cmd` (`event`/`contact`/`rating`) — просто 200 + лог,
  не обрабатываются.
- **Ещё не сделано / нужно на живом ключе**: `healthcheck()` не гонялся вживую, реальные значения
  `status` в истории не собраны (код умеет логировать WARNING на неизвестные, не падает), реальный
  формат номера телефона и число каналов записи не подтверждены на боевых данных — только на
  примерах из документации (`tests/fixtures/kcell_history.json` — синтетика, не боевой дамп).
  `.env` нужны `TELEPHONY_PROVIDER=kcell`, `KCELL_BASE_URL`, `KCELL_API_KEY`, при включении вебхука
  ещё `KCELL_CRM_TOKEN`.

## Архитектура — модули и куда смотреть

```
                    ┌─────────────┐
  Сипуни/Kcell ────▶│  ingest     │  src/sipuni_client.py (или будущий kcell_client.py)
  (звонки+запись)   └─────┬───────┘
                          ▼
                    ┌─────────────┐
                    │  STT        │  src/stt.py (Whisper/Deepgram/Yandex) + src/elevenlabs_stt.py
                    │  → сегменты │  Контракт: list[{speaker, start, end, text, lang}]
                    └─────┬───────┘  STT_MODE=route: Deepgram сначала, если непохоже на русский —
                          ▼          эскалация на ElevenLabs (казахский)
                    ┌─────────────┐
                    │  LLM-анализ │  src/analyzer.py — промпт собирается из configs/*.yaml
                    │             │  (чеклист, ред-флаги — БЕЗ правки кода, только конфиг)
                    └─────┬───────┘  src/llm_client.py — Anthropic/Gemini/Grok/Mock
                          ▼          src/metrics.py — talk ratio, паузы СЧИТАЕТ КОД, не LLM
                    ┌─────────────┐
                    │  БД         │  src/db.py (SQLAlchemy) + src/store.py (запись)
                    │  Postgres/  │  Несвязанные по номеру звонки → mapping_unmatched,
                    │  SQLite     │  ничего не теряется
                    └─────┬───────┘
                    ┌─────┴───────┐
                    ▼             ▼
              ┌──────────┐  ┌──────────┐
              │ дашборд  │  │ Bitrix24 │  dashboard/app.py (FastAPI)
              │ FastAPI  │  │ карточка │  src/bitrix_client.py — пишет разбор в timeline+поля сделки
              └──────────┘  └──────────┘

  src/pipeline.py — оркестратор всего (process_period() — боевой проход за период)
  src/runtime.py  — общая сборка LLM/STT-движков из env (используют run_production.py,
                    scheduler.py, run_local_audio.py — не дублировать эту логику снова)
```

### Точки входа

| Файл | Назначение |
|---|---|
| `run_production.py DD.MM.YYYY DD.MM.YYYY [--limit N]` | Боевой прогон за период. `--limit N` — ограничить число РЕАЛЬНО обработанных (платных STT+LLM) звонков — использовать для тестов, чтобы не улететь на весь день трафика. |
| `scheduler.py` | Демон: раз в `INGEST_EVERY_MIN` (по умолчанию 30) тянет новые звонки, вечером шлёт сводку в Telegram, раз в день синкает сделки из Bitrix (`sync_deals`). Сейчас НЕ задеплоен как отдельный сервис на Railway — считает по выбору пользователя ("пока только дашборд"). |
| `run_local_audio.py [папка] [лимит] [пауза]` | Локальный прогон реальных mp3 (без Sipuni/Bitrix) — для проверки качества STT+анализа на боевых записях. Автоопределяет stereo/mono по файлу. |
| `dashboard/app.py` | `uvicorn dashboard.app:app` — веб-дашборд + `POST /webhook/kcell` (push вместо опроса, второй этап). |
| `seed_and_report.py` | Демо-данные + консольный отчёт «где деньги» — без ключей, для локальной проверки. |
| `setup_managers.py [--apply]` | Заводит менеджеров в БД из `/users` Kcell (роль `user`/`group_head`, фильтр ботов/тестовых по имени). **На боевой БД сначала `tools/migrate_manager_keys.py --apply`** (см. ниже), иначе таблица ещё старой схемы. |
| `tools/migrate_manager_keys.py [--apply]` | Разовая миграция схемы `manager`/`mapping_unmatched` под Kcell (переименование колонки + новая `kcell_login`). Идемпотентно, SQLite и Postgres. |
| `tools/probe_record.py [--days N \| файл.mp3]` | Стерео/моно + кодек/битрейт реальной записи Kcell (ffprobe) — прогнать один раз перед первым боевым прогоном, документация Kcell это не говорит. |

## Бизнес-логика — как устроен анализ

- **`analysis_schema.json`** — JSON Schema, единая точка правды по контракту разбора звонка.
- **`configs/yandex_taxi_corp.yaml`** — правила БЕЗ кода: чеклист скрипта, ред-флаг-правила (регламентные
  нарушения типа «подача до 5 минут» вместо «от»), категории результата звонка, экономика
  (`avg_deal_value`, `recovery_rate` — сейчас 0/0, то есть "не настроено", отчёт денег показывает
  честное «н/д», а не враньё нулями — см. `_fmt_money` в `src/report_money.py`).
- **Метрики (talk ratio, паузы, время реакции)** считает код (`src/metrics.py`), не LLM — модели ненадёжны
  в арифметике.
- **Роли в транскрипте** (`operator`/`client`) на реальных записях **иногда путаются** между каналами
  (наводка/перекрёстная речь на части записей — не баг с перепутанными индексами 0/1, проверено на живых
  звонках). Поэтому `src/analyzer.py` инструктирует LLM не доверять слепо ярлыку роли, если содержание
  реплики ему противоречит — это заплатка, не корневой фикс. Перед тем как полностью доверять
  чек-листам/ред-флагам в проде — сверить несколько живых разборов с аудио на слух.
- **`result_classification.primary`** — одна из категорий из `result_categories` в конфиге
  (`success`, `not_reached`, `individual_not_legal`, `wrong_number`, `aggressive`, `not_relevant`,
  `already_driving`, `call_dropped`, `reached`). Используется и в отчёте денег (`BASE_FAULT` — вина базы,
  не менеджера), и в сверке с CRM.
- **Этап 2 (конверсии)** — `src/report_conversions.py`. Таблица `Deal` наполняется из Bitrix
  (`src/bitrix_sync.py::sync_deals`), а не из телефонии. Стадии воронки (`WON_STAGES`, `KP_KDZ_STAGES`)
  **подтверждены живым запросом к реальному Bitrix-порталу** (`crm.status.list`) — не гадай их заново,
  если нужно поменять — сверяйся с реальным порталом клиента, у каждого CRM свои `STATUS_ID`.
- **`Deal.manager_id` не проставляется** — Bitrix отдаёт только `ASSIGNED_BY_ID` (ID юзера Bitrix), а
  связки «юзер Bitrix ↔ внутренний номер телефонии» в системе нет, и текущий вебхук (scope=crm) не может
  читать `user.get`, чтобы её найти. Это известное ограничение, не забытый баг.
- **Номера телефонов хранятся в разных форматах** на разных концах: `Call.client_number` — как отдаёт
  телефония (например `+77001234567`), `Deal.client_number` — канонические последние 10 цифр без кода
  страны. Сравнивать их надо по суффиксу (`LIKE %...`), не на равенство — уже дважды находил этот баг
  (в `crm_reconciliation` и `_enrich_is_legal`).

## Прод-деплой (Railway)

- Проект **`adventurous-ambition`** (workspace "Adilet's EX"), сервис **`CallAnalyzer`**,
  URL: `https://callanalyzer-production.up.railway.app`. Привязан к GitHub `877555666zzz-ai/CallAnalyzer`,
  ветка `main` — пуш в `main` = автодеплой.
- **НЕ путать с проектом `wonderful-freedom`** — это ДРУГОЕ приложение (`ZvandauBitrixSipuni`, автодозвон,
  другой стек на asyncpg), просто на том же Bitrix-портале. Если `railway status` показывает не тот
  проект — перелинковать: `railway link -p 9f21c2d1-1b0d-4fce-acd6-886d9327b858 -e production -s CallAnalyzer`.
- Postgres подключён как отдельный сервис в том же проекте, `DATABASE_URL` на сервисе `CallAnalyzer`
  ссылается на него через `${{Postgres.DATABASE_URL}}`.
- **Railway/Railpack выполняет команду запуска приложения прямо на этапе СБОРКИ образа** как проверочный
  шаг — без доступа к приватной сети сервисов. Поэтому `dashboard/app.py` НЕ должен трогать БД ни при
  импорте модуля, ни в startup-событии — только лениво, при первом реальном HTTP-запросе (см. `Session()`
  как функция, не sessionmaker, в `dashboard/app.py`). Это же продиктовало `railway.json` — там явно
  разведены `build.buildCommand` (только `pip install`) и `deploy.startCommand`, иначе Railpack
  автоматически сливает их и билд зависает на 20 минут ожидания, пока веб-сервер (который никогда сам не
  завершается) не будет принудительно убит по таймауту.
- `/healthz` — лёгкий liveness-эндпоинт без похода в БД, для healthcheck.
- **Реальных менеджеров в проде нет.** SSH/`railway connect` на эту машину не проходит (личный ключ
  пользователя защищён паролем, я не могу его разблокировать в неинтерактивном окружении) — популяция
  менеджеров через `setup_managers.py --apply` должна выполняться самим пользователем через
  `railway connect Postgres --tunnel-only` в его собственном терминале. **Порядок:** сначала
  `tools/migrate_manager_keys.py --apply` (боевая БД ещё на старой схеме Sipuni), потом
  `setup_managers.py --apply` (теперь тянет `/users` Kcell, не Sipuni-операторов).
- **На Railway уже заданы `TELEPHONY_PROVIDER=kcell`/`KCELL_BASE_URL`/`KCELL_API_KEY`** (проверено
  `railway variables --service CallAnalyzer` 24.08.2026) — живой ключ теперь физически подключён,
  но прогон на реальных данных с него ещё не делали (см. «Пагинация не подтверждена»,
  «Стерео/моно не задокументировано» выше — это по-прежнему актуально, ключ есть, а живой прогон — нет).
- **Автозабор (scheduler.py) не задеплоен** как отдельный сервис — сознательный выбор пользователя,
  пока данные заводятся вручную через `run_production.py --limit N`.
- **Запись в Bitrix ни разу не проверялась на живой сделке** — тестовые прогоны намеренно делались с
  `BITRIX_WEBHOOK=""` (пустая строка, НЕ unset — `run_production.py` сам перечитывает `.env` через
  `setdefault`, поэтому `env -u BITRIX_WEBHOOK` не работает, только пустая строка реально отключает).

## Известные ограничения / чего не чинить бездумно

- `YandexSTT.transcribe()` — намеренная заглушка (`NotImplementedError`), не баг.
- Роли по паролям (`dashboard/app.py::_AuthMiddleware`): `ROP_USER`/`ROP_PASS` — доступ только
  к `/rop`, `/tops`, `/calls`, `/audio`; `BOSS_USER`/`BOSS_PASS` — без ограничений. Старая единственная
  пара `DASHBOARD_USER`/`DASHBOARD_PASS` ещё поддерживается как алиас на полный доступ (миграционная
  совместимость), но новые деплои настраивать через `ROP_*`/`BOSS_*`. Ни одна пара не задана на
  проде на 24.08.2026 — дашборд полностью открыт, включить до реальных звонков с ПДн клиентов.
  **С 24.08.2026 логин — не HTTP Basic, а своя форма (`/login`) + подписанная cookie-сессия**
  (`SessionMiddleware`, требует `itsdangerous`): попап браузера нельзя было ни стилизовать, ни развести
  на два разных домашних экрана после входа. Экран после логина зависит от роли — РОП сразу попадает на
  `/rop` и видит в навбаре только «РОП»/«Топы»/«Звонки» (не видит «Где деньги»/«Конверсии»/«Забор»/
  «Загрузить» — ни в меню, ни по прямой ссылке, оба уровня защиты синхронны); руководитель — на `/boss`
  (сводка «одним экраном») и видит всё. Без `SECRET_KEY` в окружении сессии переживают процесс, но
  сбрасываются на каждом рестарте/деплое (в проде стоит задать явно, чтобы не разлогинивало на каждый пуш).
- `configs/yandex_taxi_corp.yaml` → `economics`: `avg_deal_value`/`recovery_rate` = 0 намеренно (см. выше).
- В чате раньше палились настоящие ключи (Anthropic/Bitrix/Deepgram/ElevenLabs/Sipuni) — стоит перевыпустить,
  если ещё не сделано.

## Быстрые команды

```bash
source venv/bin/activate
python seed_and_report.py                          # демо-данные + отчёт в консоль, без ключей
uvicorn dashboard.app:app --port 8000               # дашборд локально (DATABASE_URL=sqlite:///out/demo.db по умолчанию)
python run_production.py 01.08.2026 01.08.2026 --limit 3   # осторожный боевой тест
railway status                                      # проверить прод (нужен линк на adventurous-ambition/CallAnalyzer)
railway logs --build -n 50 <deployment-id>           # логи сборки конкретного деплоя

# Kcell (перед первым боевым прогоном на реальном ключе)
python tools/migrate_manager_keys.py --apply        # один раз на боевой БД (Sipuni-схема -> новая)
python setup_managers.py --apply                    # менеджеры из Kcell /users
python tools/probe_record.py --days 3                # стерео/моно реальной записи (ffprobe)
python tests/test_kcell_client.py                   # map_row на синтетической фикстуре, без сети
```
